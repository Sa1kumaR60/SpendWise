## ABSTRACT

Personal financial management is a critical practical skill that students and early-career professionals often struggle to maintain due to frictionless micro-transactions across digital wallets, cards, and payment apps. Traditional tracking mechanisms such as paper ledgers and manual spreadsheets are labor-intensive, lack automated validation, and fail to alert users prior to budget overruns. Conversely, commercial financial applications frequently impose subscription fees, enforce rigid workflows, and mandate third-party banking synchronization, exposing sensitive financial history to external aggregation servers.

**SpendWise** is a lightweight, self-contained, privacy-focused personal budgeting and expense tracking platform built using the **MERN** stack (MongoDB, Express.js, React 18, and Node.js). SpendWise provides an educational, zero-bank-dependency solution where users record income and expenses, organize transactions through segregated categories, configure monthly spending caps, and analyze trends through interactive Chart.js visualizations.

Security is implemented as a primary engineering requirement: authenticated sessions are managed via signed **JSON Web Tokens (JWT)** transmitted strictly through `httpOnly`, `sameSite: 'lax'` cookies, completely immunizing the client against Cross-Site Scripting (XSS) credential theft. Passwords are cryptographically salted and hashed using `bcryptjs` with 10 salt rounds. Multi-tenant data isolation is enforced at the database level by binding every read, write, and deletion query to `req.user._id`, eliminating Insecure Direct Object Reference (IDOR) vulnerabilities.

The core budgeting engine incorporates a server-side MongoDB aggregation pipeline (`$match`, `$group`, `$sum`) to compute real-time category spending. It drives a deterministic 3-tier threshold state machine: **Normal ($<80\%$)**, **Warning ($80\%–99\%$)**, and **Exceeded ($\ge 100\%$)**, backed by proactive dashboard alert banners. Database integrity is guaranteed through compound unique indexes and referential category deletion guards, while data portability is ensured via RFC 4180-compliant CSV exports with formula-injection defenses. The system was validated through **19 automated integration tests** executed via Jest and Supertest against an in-memory MongoDB server, achieving a 100% pass rate.

**Keywords:** SpendWise, MERN Stack, Expense Tracker, Budget Management, MongoDB Aggregation Pipeline, JWT, HTTP-Only Cookie, Bcrypt, IDOR Mitigation, Multi-Tenant Isolation, RFC 4180, Chart.js.

# CHAPTER 1: INTRODUCTION

### 1.1 Background and Context
Personal financial literacy and expense discipline have become vital skills for university students and early-career software professionals. The ubiquitous adoption of digital payment systems—including Unified Payments Interface (UPI), digital wallets, tap-and-pay debit cards, and micro-subscription billing—has eliminated the friction traditionally associated with cash disbursement. Consequently, individuals routinely execute dozens of discretionary micro-transactions every week for food deliveries, daily transit, academic supplies, digital services, and leisure.

While each individual transaction represents a negligible sum, their cumulative aggregate often forms the dominant portion of an individual’s monthly outgo. In the absence of continuous, organized tracking, spending visibility is discovered only post-facto when bank balances are depleted at month-end. Recovering from unmonitored financial deficits often creates significant personal stress. Effective personal budgeting requires three core operational tenets:
1. Low-friction logging of income and expense events at the moment of commitment.
2. Contextual classification of transactions into distinct, meaningful categories.
3. Continuous comparison of running expenditures against predetermined spending limits while the monthly cycle is still active.

Modern web technologies enable the development of accessible, lightweight budgeting systems that operate natively within any browser environment. The **MERN stack**—comprising MongoDB, Express.js, React 18, and Node.js—provides a uniform JavaScript runtime across the presentation, application, and persistence tiers. This uniformity streamlines data serialisation, reduces context-switching, and facilitates the development of robust, production-tested software within a time-boxed internship.

### 1.2 Project Overview
**SpendWise** is a full-stack personal budget and expense tracking web platform designed to provide automated financial organization, proactive budget threshold alerts, and cash-flow reporting. Within SpendWise, an authenticated user records income deposits and expense purchases, binds each transaction to structured categories, configures monthly category expenditure limits, and monitors real-time financial health via an interactive executive dashboard.

The application is engineered around four core principles:
- **Privacy by Design:** All user financial records are isolated within the application's internal database; no third-party bank screen-scraping or financial aggregators are ever accessed.
- **Proactive Threshold Feedback:** Monthly category budgets are evaluated on-the-fly against live transaction data to display instant warnings before overspending occurs.
- **Engine-Level Relational Integrity:** Uniqueness constraints, multi-tenant isolation, and referential integrity guards are enforced at the database engine level via compound indexes and query scoping.
- **Complete Data Portability:** Users retain absolute ownership of their financial records through RFC 4180-compliant CSV exports with active formula-injection defenses.

### 1.3 Need for the Project
Unregulated personal spending leads to cumulative fiscal distress. Traditional personal finance management approaches suffer from significant operational shortcomings:
1. **Manual Inefficiency:** Physical ledgers depend entirely on manual arithmetic, offer zero search capabilities, and cannot alert users when limits are approached.
2. **Formula Vulnerability in Spreadsheets:** Desktop and cloud workbooks (Excel, Google Sheets) require continuous formula maintenance. A single corrupted cell reference or misplaced sort range invalidates financial summaries.
3. **Privacy Invasions in Commercial Applications:** Free-tier commercial budgeting platforms monetize user behavior by requiring live bank logins, replicating entire banking histories onto third-party marketing servers.
4. **Data Lock-In:** Proprietary budgeting software routinely restricts basic features like multi-category reporting or CSV data export behind premium monthly paywalls.

SpendWise eliminates these barriers by providing an automated, self-contained, privacy-centric alternative designed specifically for personal and academic budget governance.

### 1.4 Problem Statement
Existing manual budgeting techniques are labor-intensive, error-prone, and passive, while commercial personal finance applications compromise personal data privacy through third-party banking integration and subscription paywalls. There exists a clear necessity for an accessible, secure, multi-tenant web application that reliably logs transactions, guarantees tenant data privacy, calculates monthly budget limits dynamically, and provides actionable visual financial intelligence without external banking dependencies.

### 1.5 Aim and Objectives
The overarching aim of this project is to analyze, architect, develop, and verify a secure, responsive MERN web platform that automates personal expense recording and budget threshold monitoring. The technical objectives are:
1. **Architect Secure Session Management:** Implement user registration and authentication utilizing `bcryptjs` password hashing (10 salt rounds) and stateless JSON Web Tokens delivered strictly via `httpOnly`, `sameSite: 'lax'` cookies.
2. **Enforce Multi-Tenant Data Isolation:** Eliminate Insecure Direct Object Reference (IDOR) vulnerabilities by binding all database operations to `req.user._id`.
3. **Build an Advanced Transaction Engine:** Implement complete CRUD functionality supporting regex text searching, multi-criteria filtering, multi-field sorting, and server-side pagination ($10\text{ records/page}$).
4. **Engineer an Automated Budget Aggregation Pipeline:** Implement a real-time MongoDB aggregation pipeline (`$match`, `$group`, `$sum`) to evaluate category spending against limits, driving a 3-tier state machine (Normal $<80\%$, Warning $80\%–99\%$, Exceeded $\ge 100\%$).
5. **Ensure Data Integrity & Export Standards:** Enforce engine-level uniqueness via compound indexes, protect against orphaned records via category deletion guards, and implement RFC 4180 CSV serialization with spreadsheet formula-injection defense.
6. **Validate via Automated Integration Testing:** Author and execute an automated test suite comprising 19 integration tests across 4 suites using Jest, Supertest, and an in-memory database.

### 1.6 Scope and Boundaries
The operational scope encompasses user authentication; profile customization; segregated category creation; income/expense transaction logging; keyword search, filtering, and pagination; monthly budget definition; dynamic progress computation; visual chart rendering; dark/light theme toggling; and CSV statement generation.

The following capabilities are deliberately excluded from the current educational scope: direct integration with core banking APIs (e.g., Plaid), automated SMS parsing, OCR receipt scanning, and real-time foreign currency conversions. These capabilities are cataloged in Chapter 7 as future enhancements.

# CHAPTER 2: LITERATURE SURVEY AND EXISTING SYSTEMS

### 2.1 Existing System Overview
Personal financial management systems historically fall into three categories: manual paper ledgers, spreadsheet workbooks, and commercial web/mobile aggregators. Each approach represents distinct trade-offs regarding friction, accuracy, cost, and privacy.

### 2.2 Traditional Tracking Approaches and Limitations
Manual physical ledgers require manual entry and mental arithmetic, rendering them vulnerable to calculation drift and physical loss. Spreadsheet software (Microsoft Excel, Google Sheets) represents an advancement by automating calculations via formulas. However, spreadsheets lack application-level validation: accidental formula overwrites, range truncations, or unsorted ranges silently corrupt totals. Furthermore, spreadsheets lack native multi-tenant boundaries on shared computers and provide no proactive alerting mechanisms when spending approaches critical limits.

| Existing System Issue | Operational Impact |
|---|---|
| **Manual Arithmetic** | Arithmetic errors compound unnoticed until bank reconciliation. |
| **Absence of Validation** | Negative amounts, missing timestamps, and malformed strings corrupt summaries. |
| **Category Inconsistencies** | Free-text variations ("Food", "food", "Dining") fragment spending aggregations. |
| **Zero Proactive Warnings** | Budget exceedances are identified only after monthly statements are generated. |
| **Inadequate Access Controls** | Files stored locally or shared via links expose private balances to unauthorized viewers. |
| **Formula Corruption** | Inadvertent keystrokes corrupt cell reference formulas silently. |

*Table 2.1: Operational Defects of Manual and Spreadsheet Tracking*

### 2.3 Commercial Budgeting Applications and Privacy Risks
Commercial platforms (e.g., YNAB, Mint) provide automated bank statement synchronization and graphical dashboards. However, their architecture introduces critical concerns:
1. **Privacy Violations:** Automatic transaction import relies on third-party aggregators that store bank credentials or API tokens, replicating personal financial histories across external commercial servers.
2. **Subscription Paywalls:** Premium features (custom reporting, multi-budget tracking, CSV exports) are routinely restricted behind recurring monthly or annual subscription fees.
3. **Third-Party Breach Surface:** Financial aggregators represent centralized attack targets. Compromising an aggregator exposes credentials and transaction records across thousands of institutions.
4. **Vendor Lock-In:** Commercial solutions utilize proprietary storage formats, making migration or independent auditing cumbersome.

### 2.4 Proposed SpendWise Architecture
SpendWise is engineered as an open, self-contained, privacy-first web application. Built on the MERN stack, it executes as a private three-tier system: React 18 on the presentation tier, Express 4 and Node.js on the application tier, and MongoDB on the persistence tier. SpendWise requires no third-party financial connections; users log transactions directly into an optimized interface with one-click demo data provisioning for review.

### 2.5 Multi-Factor Comparative Analysis

| Feature Dimension | Manual Ledgers | Spreadsheets (Excel) | Commercial Apps (YNAB) | SpendWise (Proposed) |
|---|---|---|---|---|
| **Data Entry** | Manual paper | Manual cell entry | Automated bank sync | Optimized manual form |
| **Calculation Integrity** | Low (human error) | Moderate (formula bugs) | High | Absolute (Server aggregation) |
| **Proactive Alerts** | None | Manual conditional styles | Push notifications | Built-in 3-tier state machine |
| **Data Privacy** | Physical exposure | Local file exposure | Third-party shared | 100% User-scoped, self-hosted |
| **Authentication** | None | File password | Account / OAuth | Bcrypt + HTTP-only JWT |
| **Multi-Tenant Isolation** | N/A | File-level | Cloud vendor | Enforced via `req.user._id` |
| **Licensing Cost** | Negligible | Office license | $15–$100 / year | 100% Free, Open-Source Stack |
| **Data Portability** | Manual copying | Native workbook | Restricted export | RFC 4180 CSV with injection shield |
| **Automated Testing** | None | None | Proprietary internal | 19 automated integration tests |

*Table 2.2: Multi-Factor Comparative Matrix*

### 2.6 Technical Justification of Proposed Solution
SpendWise delivers automated aggregation, proactive threshold monitoring, multi-tenant isolation, and complete data portability at zero licensing cost. Excluding external banking APIs is an intentional architectural decision: it minimizes attack surfaces, eliminates regulatory compliance overhead, and keeps project delivery focused on full-stack software engineering principles.

# CHAPTER 5: IMPLEMENTATION AND SECURITY

### 5.1 Development Environment and Build Tooling
SpendWise runs with decoupled frontend and backend development environments. The React frontend is served by Vite on port `5173`, featuring Hot Module Replacement (HMR). The Express API server runs on port `5000`. Vite proxies `/api` requests to `http://127.0.0.1:5000`, ensuring cookies are treated as first-party assets. Environment configurations are isolated in `.env` files and excluded from source control.

### 5.2 Authentication and Session Architecture (Cookie vs. LocalStorage)
Upon authentication, the server generates a signed JSON Web Token (RFC 7519) and sets it in an HTTP-only cookie:

```javascript
const token = jwt.sign({ id: user._id }, process.env.JWT_SECRET, { expiresIn: '7d' });
res.cookie('token', token, {
  httpOnly: true,
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'lax',
  maxAge: 7 * 24 * 60 * 60 * 1000,
});
```

```
[ Browser Client ]                  [ Express API Server ]                  [ MongoDB Engine ]
        │                                     │                                      │
        │─── POST /api/auth/login ───────────>│                                      │
        │    { email, password }              │─── User.findOne({ email }) ─────────>│
        │                                     │<── Returns user document + hash ─────│
        │                                     │                                      │
        │                                     │ [ bcrypt.compare(pass, hash) ]       │
        │                                     │ [ jwt.sign({ id: user._id }) ]       │
        │<── 200 OK + Set-Cookie: token ──────│                                      │
        │    (HttpOnly; SameSite=Lax)         │                                      │
```
*Fig 5.1: HTTP-Only Cookie Authentication and Token Verification Flow*

| Security Dimension | `localStorage` + Bearer Header | HTTP-Only, SameSite=Lax Cookie (SpendWise) |
|---|---|---|
| **JavaScript Accessibility** | Completely accessible via `window.localStorage` | Inaccessible to client-side scripts (`httpOnly: true`) |
| **XSS Attack Vulnerability** | Vulnerable: Injected scripts exfiltrate tokens | Immune: Tokens cannot be extracted via scripts |
| **CSRF Exposure** | None (Header attached manually) | Mitigated via `SameSite: 'lax'` attribute |
| **Session Invalidation** | Requires client-side script execution | Handled directly by server clearing cookie |

*Table 5.1: Session Storage Security Comparison: HTTP-Only Cookie vs. LocalStorage*

### 5.3 Password Cryptography Implementation
Passwords are never stored in plaintext. SpendWise uses `bcryptjs` within a Mongoose pre-save hook:
```javascript
userSchema.pre('save', async function (next) {
  if (!this.isModified('password')) return next();
  const salt = await bcrypt.genSalt(10);
  this.password = await bcrypt.hash(this.password, salt);
  next();
});
```
Bcrypt applies an adaptive work factor ($2^{10} = 1024\text{ iterations}$) and generates a unique 128-bit salt per user, neutralizing precomputed rainbow-table attacks. Constant-time comparisons eliminate timing attack vulnerabilities.

### 5.4 Multi-Tenant Data Isolation and IDOR Defense
Insecure Direct Object Reference (IDOR) vulnerabilities occur when servers trust client-supplied document IDs without verifying ownership. SpendWise eliminates IDOR by binding every query to the verified `req.user._id`:
```javascript
// Strict Tenant-Scoped Lookup
const transaction = await Transaction.findOne({ _id: req.params.id, user: req.user._id });
if (!transaction) {
  return res.status(404).json({ success: false, message: 'Transaction not found or access denied.' });
}
```
Attempting to access another user's document ID returns an HTTP 404 status, avoiding confirmation of document existence.

### 5.5 Transaction Management and Advanced Query Engine
The transaction listing endpoint builds MongoDB queries dynamically based on validated query parameters:
```javascript
const filter = { user: req.user._id };
if (type) filter.type = type;
if (category) filter.category = category;
if (startDate || endDate) {
  filter.date = {};
  if (startDate) filter.date.$gte = new Date(startDate);
  if (endDate) filter.date.$lte = new Date(endDate);
}
if (search) {
  const safeRegex = new RegExp(search.trim().replace(/[.*+?^${}()|[\]\\]/g, '\\$&'), 'i');
  filter.$or = [{ description: safeRegex }, { notes: safeRegex }];
}
const transactions = await Transaction.find(filter)
  .populate('category', 'name color icon')
  .sort({ [sortBy]: sortOrder === 'asc' ? 1 : -1 })
  .skip((page - 1) * limit)
  .limit(limit);
```
Server-side pagination limits payload sizes, preserving predictable client memory consumption.

### 5.6 Proactive Budget Threshold Engine and Aggregation Algorithm
Budget spending is computed directly inside MongoDB using an aggregation pipeline:

```javascript
const spendingAgg = await Transaction.aggregate([
  {
    $match: {
      user: req.user._id,
      type: 'expense',
      date: { $gte: startDate, $lte: endDate },
    },
  },
  {
    $group: {
      _id: '$category',
      totalSpent: { $sum: '$amount' },
    },
  },
]);
```
*Fig 5.2: Real-Time Budget Aggregation and Threshold Pipeline*

#### Mathematical Formulation
Let $L$ represent the configured budget limit for a category and $S$ represent the cumulative sum of expenses within the month:
$$S = \sum_{i=1}^{n} a_i, \quad P = \left(\frac{S}{L}\right) \times 100$$
where $a_i$ denotes the amount of transaction $i$. The budget state is governed by a piecewise function:

$$\text{State}(P) = \begin{cases} 
\text{Normal}, & P < 80\% \\ 
\text{Warning}, & 80\% \le P < 100\% \\ 
\text{Exceeded}, & P \ge 100\% 
\end{cases}$$

```
   P < 80%                     80% <= P < 100%                     P >= 100%
+------------+               +-----------------+               +---------------+
|   NORMAL   | ────────────> |     WARNING     | ────────────> |   EXCEEDED    |
| (Green Bar)| <──────────── | (Amber Banner)  | <──────────── | (Red Alert)   |
+------------+  Transaction  +-----------------+  Transaction  +---------------+
                  Deleted                           Deleted
```
*Fig 5.3: Three-Tier Budget Threshold State Machine*

| State Tier | Condition Range | UI Rendering & Visual Feedback |
|---|---|---|
| **Normal** | $P < 80\%$ | Green progress bar (`#16a34a`); standard spending indicator. |
| **Warning** | $80\% \le P < 100\%$ | Amber progress bar (`#d97706`); proactive top alert banner listing category. |
| **Exceeded** | $P \ge 100\%$ | Crimson red bar (`#dc2626`); alert banner showing overspend deficit amount. |

*Table 5.2: Budget Threshold State Machine Classifications*

### 5.7 Category Management and Referential Deletion Guards
Because MongoDB does not enforce foreign keys automatically, deleting a referenced category would create orphaned records. SpendWise enforces referential integrity through pre-deletion checks:
```javascript
const txCount = await Transaction.countDocuments({ user: req.user._id, category: id });
const budgetCount = await Budget.countDocuments({ user: req.user._id, category: id });
if (txCount > 0 || budgetCount > 0) {
  return res.status(400).json({
    success: false,
    message: `Cannot delete category: in use by ${txCount} transaction(s) and ${budgetCount} budget(s).`,
  });
}
await Category.deleteOne({ _id: id });
```

### 5.8 Data Portability and RFC 4180 CSV Serialization
The CSV export engine serializes records adhering to RFC 4180 standards:
```javascript
const escapeCsvCell = (val) => {
  if (val === null || val === undefined) return '""';
  let str = String(val);
  // Defuse CSV formula injection
  if (/^[=+\-@\t\r]/.test(str)) str = "'" + str;
  if (str.includes('"') || str.includes(',') || str.includes('\n')) {
    return `"${str.replace(/"/g, '""')}"`;
  }
  return `"${str}"`;
};
```
Prepending a single quote (`'`) to cells starting with formula symbols (`=`, `+`, `-`, `@`) neutralizes spreadsheet formula execution attacks.

### 7.2 Known System Limitations
- **Manual Transaction Entry:** In accordance with the privacy-first design, transactions are entered manually rather than synced automatically via commercial bank feeds.
- **Floating-Point Arithmetic:** Monetary values are modeled as standard JavaScript numbers. High-frequency enterprise financial systems typically store integer cents or use `Decimal128` to avoid binary floating-point rounding.
- **Single Active Base Currency:** Currency preferences format visual currency symbols ($ , € , £ , ₹$) but do not execute dynamic foreign exchange conversions.
- **Stateless Token Revocation:** JWTs remain valid until expiration. Instant invalidation prior to expiration would require a token deny-list or Redis cache.

### 7.4 Conclusion and Technical Retrospective
SpendWise demonstrates that a well-architected full-stack web application can provide automated, private, and proactive personal financial tracking. By combining React 18, Express, Node.js, and MongoDB, the system replaces error-prone manual ledgers and intrusive commercial applications with a self-contained, user-isolated platform.

The internship provided valuable technical experience across the software development lifecycle:
- Selecting **HTTP-only cookies** over `localStorage` eliminated XSS credential extraction risks.
- Structuring all database queries with **`req.user._id`** established tenant isolation as an architectural pattern rather than an afterthought.
- Enforcing constraints via **compound unique indexes** proved more reliable than application-level checks under concurrent request conditions.
- Adopting **in-memory database testing** enabled rapid, safe regression testing during development.

In conclusion, SpendWise serves as an effective academic and practical demonstration of modern full-stack web engineering, secure software architecture, and user-centric application design.
